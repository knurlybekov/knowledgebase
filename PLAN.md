## Goal

An authenticated member of an organization links a Google Drive or SharePoint account, the platform syncs the documents that account can see, and the member gets grounded answers with citations (Quick Search) or a multi-step cited investigation through Hermes (Deep Investigation) over exactly the document revisions they are allowed to see, as of the last complete access revalidation of that scope and never older than a configured bound. Documented decisions can be proposed by the agent as candidates and verified by a steward. Every access path is server-side authorized, organization-isolated by Postgres RLS plus explicit predicates, and audited.

## Key decisions and tradeoffs

**D1. Hermes runs as one isolated process per investigation (ADR).** A runner service (FastAPI, inside the `hermes-agent` image, using the Hermes venv's own FastAPI and uvicorn) receives `{run_key, question, instructions, limits, mcp_token}` from the backend over an internal network with a shared-secret bearer. For each run it creates `/opt/data/runs/<run_key>/` (mode 0700) as `HERMES_HOME` holding a generated `config.yaml`: `mcp_servers.knowledge.url`, `headers.Authorization: "Bearer ${KNOWLEDGE_MCP_TOKEN}"`, `memory.memory_enabled: false`, `memory.user_profile_enabled: false`, toolsets restricted to `mcp-knowledge`, `approvals.single_query_mode: deny`. The investigator instructions are written as the run's context file (`AGENTS.md` in the run cwd; the spike confirms the exact file and that the injection scanner accepts it; fallback is prepending to the query). It then starts `hermes chat -q <question> --toolsets mcp-knowledge --max-turns N --format stream-json` with stdin closed (non-TTY implies one-shot), `HERMES_HOME` and `KNOWLEDGE_MCP_TOKEN` in the environment, in a new process group. `--ignore-user-config` is not used (verified in `hermes_cli/_parser.py` at v0.22.1: it ignores `config.yaml`); `--ignore-rules` is not used (skips context files); `--safe-mode` is not used (disables MCP). The model never sees the token. Cancel sends SIGINT to the process group, then SIGKILL after a grace period. **Process identity:** the runner registry stores `run_key, pgid, process start time (psutil create_time), container boot id, dir`; at startup it signals a recorded group only if pgid + start time + boot id all match a live process, otherwise it only erases the directory. **Configuration attestation:** before the first run after each image build, the runner executes the pinned invocation against a self-check MCP server and asserts that the enabled tool names are exactly the `mcp_knowledge_*` set and that no `terminal`, `browser`, `web`, `file`, `memory`, `session_search`, `skills` or `delegation` tool is present; the attestation result is stored and the runner refuses runs if it fails. Trusted-runtime boundary: all runs share one container, one uid and one filesystem; secrets in the container are the LLM provider key, the runner secret, and one capability token per run in that process's environment. Rejected alternative: the shared Hermes API server (`/v1/runs`) with the token inside `instructions`.

**D2. Local login plus verified identity links.** Custom `User` with email as username, Django sessions. `UserIdentity(user, provider, external_id, email, verified_via=oauth|admin)`. The delegated connector OAuth (D3) is the verification step. SSO later writes the same table.

**D3. Per-user delegated connector credentials (Karen's decision over the recommendation).** Each user links their own Microsoft or Google account; the crawl runs as that user. **Grants bind to content revisions:** `AccessGrant(document, link, version)` records that this link's crawl observed this revision. A user sees a document version only through a valid grant of one of their links. Storage dedupes by canonical source identity: one document, one chunk set per `(document, version_label)`. **Authorization promise (explicit):** a user sees what their account could see at the last *complete access revalidation* of that scope, and never anything older than `PERMISSION_FRESHNESS_MAX_AGE` (default 24 h). **Revalidation protocol (Codex round 3):** incremental polling health does not renew grants. A grant is revalidated only when (a) an inbox event for that item is applied, or (b) a complete scope revalidation (`full_reconcile`: a full re-enumeration of what the account can see, metadata only, no downloads for unchanged content) completes and the item is in it. `AccessGrant.last_revalidated_at` records the **observation time** (the timestamp at which the provider returned the item: the sync page's fetch time, stored on the inbox row as `observed_at`), not the processing time, so a delayed inbox item cannot open a fresh 24 h window (tested with delayed processing). `FULL_RECONCILE_INTERVAL` defaults to 12 h, half of `PERMISSION_FRESHNESS_MAX_AGE`, so a healthy system never lets grants expire while an unhealthy or incomplete reconcile lets them expire on schedule. Incremental feeds still apply explicit removals immediately (Graph `deleted` facet; Google `removed: true`), but the design does not rely on them to report inherited or group permission loss. A link in `error` or `revoked` status invalidates all of its grants at once. An expiration sweeper purges versions whose grants are all stale beyond `PERMISSION_FRESHNESS_MAX_AGE + PURGE_GRACE`. Consequence recorded: documents that only a departed user's crawl reached go dark (fail closed).

**D4. Server-rendered UI.** Django templates + HTMX + Tailwind. HTMX polling for investigation status. JSON endpoints under `/api/v1/` as plain Django views with pydantic request models.

**D5. Short transactions with organization scope.** `OrgAwareTask` carries `organization_id` and sets a ContextVar only. Every database write happens inside a short `with_org(organization_id)` block that opens `transaction.atomic()`, sets `SET LOCAL app.org_id` and `SET LOCAL app.actor_id`, and commits. External calls (connector HTTP, embeddings, runner streaming) run outside transactions. Locks that must span external calls are durable leases with fencing tokens, not advisory locks (see Ingestion). Advisory locks (`pg_advisory_xact_lock`) are used only inside single short transactions (publish, revoke, purge of one document).

**D6. Derived text follows its evidence (Codex round 2).** Answers, investigation results and decision records are authorized against *all* evidence supplied to their generation, not only cited evidence. If any supplied evidence is no longer visible to the reader, the whole object is withheld. If any supplied evidence is purged, all text-bearing fields of the derived object are purged. There is no declassification path in this release: the `organization` visibility mode for decision records is removed; records are `evidence_bound` only.

**Cosmetic (accepted as a batch):** Celery + Redis + django-celery-beat; apps `accounts, organizations, connectors, knowledge, retrieval, answers, investigations, mcp_server, decisions, web, infra, eval` with `<app>/api.py` boundaries; "organization" naming and `CONTEXT.md` glossary; default embedder `openai/text-embedding-3-small` 1536-d `halfvec`, `MockEmbedder` in tests; heading-aware chunker ~800 tokens, 100 overlap, locators; RRF k=60, 50 candidates per leg, reranker protocol with no default; investigation defaults 12 turns, 20 tool calls, 180 s, 60,000 chars cumulative tool output, 1 retry; compose services as listed, only `web`/`caddy` published; pytest-django on real Postgres; decision extraction in Sprint 3 as candidates only; first slice = org + login + Google Drive (mocked) + ingest + search + RAG answer in UI; `CONTEXT.md` and `DECISIONS.md` start in the build.

## Database roles, RLS and relational consistency

- `kb_migrator`: owns the schema, runs migrations and the test suite (`CREATEDB` for test databases). `FORCE ROW LEVEL SECURITY` applies to owners, so RLS tests run as this role; authorization-path tests additionally connect as `kb_app`.
- `kb_app`: runtime role for `web`, `worker`, `beat`, `knowledge-mcp`. `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE`, no `CREATE` on any schema, `SELECT, INSERT, UPDATE, DELETE` on application tables only, no `TRUNCATE`, no direct privileges on `infra_auditlog`.
- **Audit trigger hardening:** `infra.audit_row_change()` is `SECURITY DEFINER` owned by `kb_migrator`, with `SET search_path = pg_catalog, infra, pg_temp` (pg_temp last), all referenced objects schema-qualified, `REVOKE EXECUTE ... FROM PUBLIC`, and a test as `kb_app` that creates a temporary table named like the audit table and asserts the trigger still writes to `infra.auditlog`. The trigger logs an allowlist of metadata columns per table (ids, status fields, timestamps, hashes), never content, excerpts, answer or result text, or token material.
- **RLS policy** on every organization-scoped table: `ENABLE` + `FORCE`, `organization_id = NULLIF(current_setting('app.org_id', true), '')::uuid`. **Membership has one additional policy** (Codex round 3; `FORCE` RLS applies to owners too, so a `SECURITY DEFINER` function would see nothing): `CREATE POLICY membership_self FOR SELECT USING (user_id = NULLIF(current_setting('app.actor_id', true), '')::uuid)`. The web layer sets `SET LOCAL app.actor_id` for the authenticated user in a short transaction right after login, lists the user's own active memberships with `app.org_id` unset, renders the organization picker, and then enters `with_org`. The policy is SELECT-only and bound to the actor GUC; tests run it as `kb_app` with `app.org_id` unset and assert that only the actor's rows are visible and that writes are denied. `NO_RLS_TABLES` = `accounts_user`, `accounts_useridentity`, `investigations_capabilitytoken`. `eval/test_rls_coverage.py` asserts coverage; a test as `kb_app` asserts `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` and `TRUNCATE` are denied.
- **Two independent layers:** every query function adds `organization_id = principal.organization_id` explicitly; RLS is the second net.
- **Composite constraints for every redundant relationship** (added by `RunSQL` in the creating migration; a test asserts their presence after `makemigrations --check`):
  - organization consistency: children carry `(organization_id, parent_id) REFERENCES parent (organization_id, id)`;
  - document/version consistency: `version UNIQUE (document_id, id)`; `chunk (document_id, version_id) REFERENCES version (document_id, id)`; `access_grant (document_id, version_id) REFERENCES version (document_id, id)`;
  - version/chunk consistency: `chunk UNIQUE (version_id, id)`; `decision_evidence (version_id, chunk_id) REFERENCES chunk (version_id, id)` (nullable chunk, see Purge); `investigation_evidence (version_id, chunk_id) REFERENCES chunk (version_id, id)`;
  - link/user consistency: `access_grant.link` → `connector_link`, and `connector_link (organization_id, user_id) REFERENCES membership (organization_id, user_id)`;
  - token/investigation consistency: `capability_token (investigation_id, user_id, organization_id) REFERENCES investigation (id, user_id, organization_id)` with `investigation UNIQUE (id, user_id, organization_id)`.

## Authorization rules (single implementation in `knowledge/api.py` and `investigations/api.py`)

- `Principal(user, organization, membership_role, investigation=None)`. Built from the session + active membership in `web`, or from a capability token in `mcp_server`.
- `valid_grants(principal)`: `grant.revoked_at IS NULL AND grant.last_revalidated_at >= now() - PERMISSION_FRESHNESS_MAX_AGE AND link.status = 'active' AND link.user = principal.user AND membership.status = 'active' AND user.is_active AND grant.organization_id = principal.organization_id`.
- `visible_versions(principal)`: versions with a valid grant and `content_state = 'present'`, on documents with `status = 'active'`. Retrieval, answers, MCP tools and UI only query chunks through `visible_versions`.
- **Derived objects (D6):** `Answer` and `Investigation` are readable and cancellable by their owner; organization admins see metadata only (status, timestamps, question hash), never content. On read, every version in `evidence_versions` (answers) or in `InvestigationEvidence` (investigations) is rechecked against `visible_versions`; any failure withholds the whole object including unsupported statements. `DecisionRecord` is visible to a user only if every `DecisionEvidence` version is visible to them, and only if `content_state = present`.
- Offboarding and unlinking: removing a membership, deactivating a user, or revoking a link runs one transaction that revokes the link's grants, revokes open capability tokens, and transitions `queued|dispatched|running` investigations to `cancelled`; runner cancel calls follow outside the transaction. Every MCP tool call rechecks membership and link status through `valid_grants`.

## Ingestion pipeline (source-independent, idempotent, fenced)

1. **Lease per scope.** `sync_scope(scope_id)` acquires `SyncLease` with a conditional update (`WHERE expires_at < now()`), sets `lease_token = random`, `expires_at = now() + LEASE_TTL`, renews after every page, and releases at the end. Every write of the sync (inbox rows, cursor, `SyncRun`) carries `WHERE lease.lease_token = :token`; a lost lease makes the write a no-op and the sync exits. A second sync that cannot acquire the lease exits immediately.
2. **Bootstrap.** Google: capture `startPageToken` first, then full paginated listing (`files.list` with `corpora=user`, then `drives.list` and `files.list` with `corpora=drive` per shared drive, `includeItemsFromAllDrives`, `supportsAllDrives`), then replay from the start token. Graph: initial `delta` enumerates everything per selected drive. Bootstrap is `reconcile_generation = 1`.
3. **Checkpointing.** Each page of changes is written as `ChangeInbox` rows (with `seq` increasing per scope and the run's `reconcile_generation` when the run is a bootstrap or full reconcile) together with the new cursor in one short fenced transaction. `process_inbox(scope_id)` works through pending rows in `seq` order; repeated items in a Graph delta page collapse to the last occurrence per `source_id`.
4. **Event fencing.** Every grant mutation records `AccessGrant.last_event_seq`. An inbox row whose `seq` is lower than the grant's `last_event_seq` is marked `obsolete` and skipped. Every grant or content mutation on a document (publish, fast-path refresh, revoke, purge, tombstone, reactivate) runs under `pg_advisory_xact_lock(hash(document_id))` inside one short transaction and increments `Document.generation`.
5. **Upsert path.** Resolve canonical `source_id`; read metadata; compute `version_label`: Google binary files `headRevisionId`, Google native files the monotonic `version` field, Graph `cTag` (content tag, falls back to `eTag`). Under the document lock: `get_or_create Document`, `get_or_create DocumentVersion`; if `content_state = present` and active chunks exist for that version, refresh the grant (`last_revalidated_at`, `last_event_seq`, `last_seen_reconcile_generation`) and metadata (fast path, fenced by seq and generation) and finish. Otherwise snapshot `generation`, release, and **stage** outside transactions: **validated download** (Google binary: `files.get(fileId, alt=media)` with the `version` field re-read after download and the bytes checked against `md5Checksum`; Google native: export, then re-read `version`; Graph: `/content` for the current item, then re-read `cTag`; in every case retry up to 3 times if the discriminator changed, else give up for this event; Google `revisions.get` is not used because revision access needs writer-level roles and `keepForever` retention, which `drive.readonly` readers do not have; Graph serves pinned content only for *previous* versions), parse, chunk, embed. **Publish** under the document lock in one transaction: reject if `Document.generation != snapshot` (requeue once), insert chunks and embeddings (unique `(version, position)` makes a replay a no-op), set `content_state = present`, set `Document.status = active` if it was a tombstone, upsert the grant with `last_event_seq`, increment `generation`.
6. **Remove path** (`kind = remove`, `changeType = drive` with `removed`, scope-wide 403/404, or token refresh failure): under the document lock, revoke this link's grant (`revoke_reason = removed|scope_lost|link_error`), increment `generation`, then `maybe_purge(version_id)`: if no valid grant remains for the version, purge (see below). A link-level failure sets `link.status = error`, which invalidates all of its grants immediately through `valid_grants`.
7. **Full reconciliation (complete access revalidation).** Scheduled by wall clock (`FULL_RECONCILE_INTERVAL`, default 12 h, enforced ≤ `PERMISSION_FRESHNESS_MAX_AGE / 2` at startup) and after HTTP 410. It opens a new `reconcile_generation` on the scope, re-lists everything the account can see in the scope (Graph: `delta` without token; Google: the bootstrap listing), and stamps every inbox row and every touched grant with that generation; applying such a row sets `last_revalidated_at` even when content is unchanged. **Sweep barrier:** the sweep runs only when the `SyncRun` is `completed` and no inbox row of that generation is `pending` or `failed` (a failed row blocks the sweep until it is retried successfully or superseded by a newer event for the same item); it revokes grants of the scope whose `last_seen_reconcile_generation` is older, with `revoke_reason = not_seen`. An incomplete reconcile never revokes anything, and grants it did not touch simply age toward the freshness bound.
8. **Expiration sweeper.** Periodic task: versions whose grants are all stale beyond `PERMISSION_FRESHNESS_MAX_AGE + PURGE_GRACE` (default 24 h + 48 h) are purged; grants moved to a newer version trigger `maybe_purge` on the older one.
9. **Rate limits and retries.** `connectors/http.py` honors `Retry-After`, retries 429/5xx with exponential backoff and jitter (max 5), then marks the `SyncRun` failed. Processing stops at the first failing page and resumes from the last durable cursor.

## Purge (complete dependency graph, ordered)

`purge_version(version_id)` under the document lock, in one transaction:
1. Collect dependents: `DecisionEvidence`, `InvestigationEvidence`, `Answer` rows with the version in `evidence_versions`, `Investigation` rows with `InvestigationEvidence` on the version, `DocumentReference` rows from the version.
2. Invalidate derived objects first: `Answer.content_state = purged` and null `answer_text`, `claims_json`, `unsupported_json`; `Investigation.content_state = purged` and null `result_json`, redact `activity_json` previews; `DecisionRecord.content_state = purged` for records with evidence on the version and null `description`, `recorded_rationale`, `alternatives_json`, `participants_json` (title and status remain as a tombstone); `DecisionEvidence.excerpt = NULL` and `chunk = NULL` (durable tombstone keeps `document`, `version_label`, `position`, `role`); `DocumentReference.evidence_excerpt = NULL`.
3. Delete `InvestigationEvidence` rows for the version, then `Embedding` (cascade from chunk), then `Chunk` rows.
4. Null `DocumentVersion.content_text` and `structure_json`, set `content_state = purged`.
5. If no version of the document has content, `Document.status = tombstone`.
6. Increment `Document.generation`.
Execution status and content status are separate fields everywhere (`status` vs `content_state`). Runner run directories are erased at run end and reconciled at startup; purging an investigation first cancels any non-terminal attempt (`POST /runs/{run_key}/cancel`, waiting for the terminal record) and then calls `DELETE /runs/{run_key}` for every attempt so durable runner events and terminal text are erased; the runner refuses `DELETE` on an active run; `RUNNER_RECORD_TTL` (24 h) bounds the residue if the calls fail. Tested with a purge while events are still being appended.

## Retrieval and answers

- `retrieval.search(principal, query, source_types, limit)`: candidate legs over `Chunk` joined to `visible_versions(principal)` (vector leg filtered to the current embedder's `model_id/version`, keyword leg on `search_vector`), RRF k=60, 50 per leg, optional reranker protocol. Returns chunk ids with locators; logs `RetrievalLog` with `denied_count` from a defensive post-filter recheck.
- `answers.answer_question(principal, question, source_types, k)`: bounded evidence context; `Composer.answer(question, evidence) -> {claims: [{text, evidence_indices}], conflicts: [], insufficient: bool}` with Anthropic, OpenAI and stub adapters. The `Answer` stores **all** supplied evidence (`evidence_chunk_ids`, `evidence_versions`), not only cited. **Claim validation:** a claim must reference at least one evidence index that exists; claims with none move to `unsupported_json` and render under a warning heading, never as findings. If no claim survives, `evidence_state = insufficient` and the text states that the available documents do not establish the answer. Citations carry title, validated source URL, version label, locator, excerpt.

## Hermes investigation lifecycle (idempotent, fenced by attempt)

- `start_investigation(principal, question)`: create `Investigation(status=queued, attempt=1, run_key="<id>:1", deadline_at=now+limit)` and enqueue `run_investigation(id)`. **Dispatch recovery:** the reaper re-enqueues `queued` rows older than `DISPATCH_TIMEOUT` (60 s) and `dispatched` rows without a heartbeat for `2 × heartbeat interval`.
- `run_investigation(id)`: claim with a conditional transition `queued → dispatched WHERE status='queued'` (exit if not claimed). **Mint the token here:** generate 32 random bytes, store the SHA-256 hash with `attempt`, keep the raw value in task memory only, commit. Call runner `POST /runs` with `run_key` (idempotent: an existing run returns its state); the runner starts the process only after it has persisted the run record, and the worker transitions `dispatched → running WHERE status='dispatched' AND attempt = :attempt` only after the runner acknowledges the start. Stream events with sequence numbers from `GET /runs/{run_key}/events?after=<last_event_seq>`; each event updates `activity_json` (tool name, duration, error flag), `heartbeat_at` and `last_event_seq` in short transactions `WHERE status='running' AND attempt = :attempt`. On the terminal event: parse the fixed Markdown structure (Answer / Evidence summary / Conflicts / Open questions / Statements with citations), validate every citation against `InvestigationEvidence` and recheck visibility, move unsupported statements to a separate list, then transition `running → completed WHERE status='running' AND attempt = :attempt AND content_state = 'present'`; a purge that ran during generation therefore prevents the result from being saved, and the row ends `completed` with `content_state = purged` and no text. Late or foreign completions are discarded. Every state transition in the lifecycle is conditional on both the expected status and the attempt. **Readiness gate (round 4):** the runner creates the run record and returns its acknowledgment *before* it starts the Hermes process; the worker commits `running` and only then calls `POST /runs/{run_key}/start`; a tool call that arrives while the row is still `dispatched` is therefore impossible in the normal path, and the MCP server answers such a call with a retryable `not_ready` error (tested). **Purged completion path:** when the terminal event arrives and `content_state = purged`, a separate conditional transition `running → completed WHERE status='running' AND attempt = :attempt AND content_state='purged'` writes no text, keeps `purged`, and revokes the token, so the row never stays `running`. The same publication-time evidence recheck applies when an `Answer` is saved and when a `DecisionRecord` is created or verified.
- **Retry** (runner reports exit code 2 or a provider error class, within the same task): `attempt = 2`, `run_key = "<id>:2"`, revoke the attempt-1 token and mint a new one (budgets and `deadline_at` live on the Investigation row and do not reset). **Recovery after a worker crash:** the reaper finds a `dispatched|running` row with a stale heartbeat; if `deadline_at` has not passed it revokes the current token, calls runner cancel for the old `run_key`, fetches the runner's persisted terminal record (if the old run completed, its result is consumed through the normal completion path instead of restarting), and otherwise resets the row to `queued` with `attempt + 1` so it is claimable again; past the deadline it marks the row `interrupted`.
- **Cancellation:** `cancel_investigation` transitions `queued|dispatched|running → cancelled` conditionally, revokes the token, then calls runner cancel. **Timeout:** the task enforces `deadline_at`; the runner enforces the same wall clock. **Every terminal transition revokes the token.** Terminal runner records are acknowledged with `DELETE /runs/{run_key}` after the result is committed.
- Observability: correlation ids `investigation_id`, `run_key`, `request_id`, `sync_run_id` on every log line and `AccessEvent`; metrics exported at `/metrics` on the internal network: `investigation_attempts_total`, `investigation_terminal_total{status}`, `runner_orphans_reaped_total`, `tool_calls_used`, `output_chars_used`, `investigation_duration_seconds`, `grant_revalidation_age_seconds` (now − `grant.last_revalidated_at`, max per organization), `reconcile_overdue_scopes`, `access_denied_total{path}`, `sync_checkpoint_seq`, `inbox_pending`, `purge_completed_total`, `lease_lost_total`.

## MCP server (`mcp_server`)

- FastMCP (official `mcp` SDK) in **stateless streamable HTTP** mode, served by uvicorn from the Django image. Each tool call is one HTTP request with `Authorization: Bearer <token>`.
- **Per-tool authorization unit** (one synchronous function via `sync_to_async`), in this order: (1) hash the token and look up `CapabilityToken` by hash in the global table; check `expires_at` and `revoked_at`; (2) **enter `with_org(token.organization_id)` before touching any organization-scoped row**; (3) inside that transaction, reserve budget and verify state in one statement: `UPDATE investigation SET tool_calls_used = tool_calls_used + 1 WHERE id = :id AND run_key = :run_key AND status = 'running' AND deadline_at > now() AND tool_calls_used < max_tool_calls RETURNING tool_calls_used` (no row → `limit_reached` or `not_running` error to the agent, and `AccessEvent(kind=denied)`); (4) build the `Principal`, recheck `valid_grants` membership and link status; (5) execute the ORM query through `visible_versions`; (6) serialize, then **allocate output capacity atomically**: `UPDATE investigation SET output_chars_used = output_chars_used + LEAST(:len, max_output_chars - output_chars_used) WHERE id = :id AND run_key = :run_key AND status='running' RETURNING (allocated)`; fit the response into the allocated length by trimming evidence excerpts (shortest-first, then dropping trailing results) while keeping the JSON structure valid, and record `InvestigationEvidence` only for the spans actually delivered; if the allocation is smaller than the minimum envelope (`MCP_MIN_RESPONSE_CHARS`, about 200), release the allocation and return a fixed `budget_exhausted` error payload that is not charged (tested at zero capacity and below the minimum); (7) write `AccessEvent`; commit. Initialization and discovery requests do not consume budget.
- Tools: `search_knowledge(query, source_types?, limit≤20)` → chunk-level results with `evidence_id = chunk:<uuid>@<version_label>[start:end]`, excerpt ≤ 500 chars, validated source URL (https, host allowlist per provider), title, version label, locator. `get_document(document_id, section?)` → visibility check, bounded window (≤ 8,000 chars), sections list, evidence ids for returned spans. Sprint 3: `trace_decision`, `find_related_documents`, `draft_knowledge_record` (validates that every evidence id was returned to this investigation and is still visible; creates a `candidate` record with `origin = agent`; nothing else).
- Document text is wrapped in a data envelope with a fixed notice that the content is data, control characters stripped, lengths bounded. The MCP server never executes anything derived from content.

## Runner (`hermes/runner`)

`POST /runs {run_key, question, instructions, max_turns, timeout_s, mcp_token, model?}` → creates and persists the run record without starting the process, idempotent on `run_key` (an existing run returns 200 with its state); `POST /runs/{run_key}/start` → starts the process (idempotent); `GET /runs/{run_key}/events?after=<seq>` (chunked JSONL, each event has `seq`; replay from `after`); `POST /runs/{run_key}/cancel`; `DELETE /runs/{run_key}` (acknowledge and erase the terminal record); `GET /health`; `GET /health/attestation`. Shared-secret bearer. Concurrency cap `RUNNER_MAX_CONCURRENT` (429 beyond). **Durable records:** `/opt/data/registry/<run_key>.json` holds `{pgid, start_time, boot_id, dir, state, events_path, terminal: {outcome, final_text, usage, exit_code}}`; events are appended to a per-run JSONL file so replay survives a runner restart; terminal records persist until acknowledged or `RUNNER_RECORD_TTL` (24 h). Each run: `start_new_session=True`, run dir 0700, wall-clock kill at `timeout_s`, SIGINT→SIGKILL, cleanup in `finally`, orphan reconciliation at startup with the identity check from D1.

## Connector specifics

- **Google Drive:** scopes `drive.readonly` (+ `openid email`). Bootstrap and incremental as above (`changes.list(pageToken, includeRemoved=true, includeItemsFromAllDrives=true, supportsAllDrives=true, fields=...)`). `removed: true` or `trashed` → remove path; `changeType = drive` with `removed` → scope-wide revoke. Native types exported (Docs→docx, Sheets→xlsx, Slides→pptx; export size cap) with the `version` before/after check; binary files via `files.get(alt=media)` with the `version` before/after check and `md5Checksum` verification. Canonical id `sp:<driveId>:<itemId>`; shared wrappers resolve to `remoteItem.parentReference.driveId` + `remoteItem.id`. `deleted` facet → remove path; HTTP 410 → full reconcile. Current content via `/content` with the `cTag` before/after check.

## Security model (summary for SECURITY.md)

Trust boundaries: browser → `web` (session auth, CSRF, rate limits) → service layer → Postgres under RLS as `kb_app`. `worker` holds connector tokens (Fernet) and provider keys. `knowledge-mcp` holds DB access and accepts only capability tokens, stateless, budgeted per tool call inside the scoped transaction. `hermes-agent` holds the LLM provider key and the runner secret; each run receives one capability token in its own process environment; no DB credentials, no terminal/browser/web/file tools, no memory; attested configuration. Document text is data: wrapped, bounded, never executed. Derived text follows its evidence (D6). Deletion: the purge graph above, audit allowlist, runner dir erasure. Known limitations recorded: no SSO, no reranker, Hermes behavior verified only by the Sprint 2 spike, no live connector tests, residency not solved in code, runs share one container, visibility is "as of the last complete access revalidation" bounded by `PERMISSION_FRESHNESS_MAX_AGE`, which means a permission change at the source can take up to that bound to take effect here, no organization-wide publication of decision records.
